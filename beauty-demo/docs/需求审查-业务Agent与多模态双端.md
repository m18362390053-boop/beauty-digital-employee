# 需求审查：可验证的业务 Agent、多模态与用户/运营双端

> **设计时期快照。** 本文“当前本地代码”表格和 `web/index.html` 等路径是审查时的基线，不代表 2026-10-13 实现。双端、权限、Skill版本已在后续提交实现；照片提交测试入口只保存素材，不能等同于图片理解、产品识别或视频生成。现行任务见 [成员 A 阶段交接](阶段交接-成员A底座审阅与后续工作.md)。

本文将组员的三项诉求转成开发要求与验收口径。以当前代码为审查依据；文中的新目录、接口和多模态流程属于下一阶段设计，不代表已经实现。

更新：本文保留审查时的基线描述。此后双端、权限、可读执行记录和Skill版本已实现，实际操作以 [双端权限与Skill验收](双端权限与Skill验收.md) 为准；多模态仍未纳入已完成清单。

## 一、审查结论

建议正式表述为：

> 建设一个由 Jev 驱动调度的美妆客服 Agent。运营人员可以导入、启用和验证版本化业务 Skill；用户通过专属客服界面发送文字和媒体，获得基于用户资料及产品知识的答复。客服执行、人工接管、反馈和指标形成可追溯闭环。用户端与运营端具有独立前端入口及服务端权限边界，共用同一业务后端。

三点方向成立，但要纠正三个歧义：

1. “写进 Agent 的 Skill 文档”应理解为进入 Agent 可加载的标准 Skill 资源和注册表，不是把所有内容拼进一个系统提示词。
2. “支持图片视频”应拆成文件上传、视觉理解、音频转写、产品候选匹配和基于证据回答，不能只做上传按钮。
3. “两个文件系统”应改为两个独立前端应用/目录与角色入口，不需要两台服务器或两套数据库；仅分HTML文件并不等于权限隔离。

- `server/core/skill-packages.ts`：Skill导入、启停、版本与知识。

- `server/app.ts`：现有API与统一前端入口，运营接口尚未有角色鉴权。
- `web/index.html`：用户、运营、调试控件混合展示。

## 三、需求1：Skill必须真正进入Agent运行，并能被业务人员验证

### 3.1 Skill的正式定义

一个业务Skill至少包括：
- 稳定ID、版本、名称/描述、适用与排除范围。
- SKILL.md中的执行说明与回答要求。
- 可用意图、需要的用户字段、知识范围、是否依赖知识。
- 随包知识及来源；可选的测试案例。
- 是否启用、导入时间、版本指纹。

建议标准包：

```text
skill-name/
├── manifest.json
├── SKILL.md
├── knowledge/
└── tests/cases.json       # 可选；导入与运行需另外定义，不能仅因有文件就宣称已经测试
```

本项目业务Skill与Harness原生Skill是两个集成层：
- 当前业务Skill由客服后端注册、选择和执行，Harness通过完整客服MCP工具调用这个后端。
- 若另要求Skill在Harness原生技能列表中出现，需要再做文件布局与加载适配，不能声称现有数据库记录等同于Harness原生Skill安装。
- 本轮建议继续以后端客服Agent为业务权威，实现一次业务逻辑，网页与Harness共用。

### 3.2 “写入文档”怎么落实

优先保留一个权威来源：当前数据库中的不可变版本记录。
运营端提供SKILL.md及包内容预览、版本导出；若需要本地文件适配器，可将同一版本导出到：

```text
data/skills/<skill-id>/<version>/SKILL.md
```

导出资源与数据库版本保持校验关系，不让人工编辑导出文件后默默覆盖运行版本。
上传完成必须返回版本、启用状态和生效说明；新请求使用新版本，正在运行的请求使用开始时的快照。
版本相同但内容不同应明确报冲突；支持选定旧版本回滚时，应作为显式操作实现并记录，而非覆盖历史。

### 3.3 Agent的完整执行契约

```text
请求身份与附件校验
  → 检查人工/结束状态与明确风险规则
  → 读取已确认用户资料和相关会话上下文
  → 需要时做媒体分析
  → Jev输出意图、风险、Skill建议、人工/追问需求
  → 程序执行风险优先策略
  → 加载被选中的Skill版本与相应知识
  → 生成回复、具体追问或人工通知
  → 保存执行记录与来源
  → 接收用户真实反馈并更新统计
```

模型建议与代码最终动作要分开保存。读取档案、查知识、建人工记录、写反馈是真实后端操作，不要求全部都由大模型自由决定。
用户点击反馈或明确表达反馈可触发记录；不能由模型自行把自己的回答标为“有帮助”。
只在用户确认后持久化新的档案事实，模型推断不能直接变成用户事实。

### 3.4 用业务人员看得懂的执行面板代替纯JSON

运营端每次测试显示：

| 阶段 | 最少展示内容 |
|---|---|
| 用户上下文 | 使用了哪张资料卡、版本、必要字段 |
| 媒体分析 | 附件ID、分析状态、识别片段与不确定项 |
| 决策 | 意图、风险、决策来源（Jev/规则/降级）、必要的置信信息 |
| Skill | ID、版本、职责；未选择时说明追问/兜底原因 |
| 证据 | 产品/知识文档名称、来源ID、命中的片段 |
| 回复 | 生成/模板/人工，实际模型、耗时、用量 |
| 人工 | 仅请求、已接管还是已结束，真实工单ID |
| 反馈 | 真实用户操作、统计更新时间与分母 |

JSON保留在“开发调试详情”中。无需展示或要求模型输出内部思维链；展示业务决策、证据和实际动作即可。
用户端只显示必要状态，例如“正在核对资料”“需要你确认产品名称”“等待人工”，不展示内部风险打分和后台配置。

### 3.5 验收

- 上传一个带独特业务描述和独特知识条目的Skill，在匹配问题上能看到真实选择的版本与知识引用。
- 修改到新版本后，新请求使用新内容，旧请求仍可追溯到原版本。
- 停用后不再被新请求选择；重启后启停与版本状态保留。
- 用对照案例证明没有匹配时会追问/兜底，而不是强行命中刚上传的Skill。
- 人工接管期间AI不再发布回答，反馈计数来自真实事件。
- 没配模型或连接失败时，运营端能看出服务与错误原因；用户端得到可执行的重试/人工入口，而不是要求客户自己配置Key。

## 四、需求2：多模态要拆成图片理解、视频画面与视频音频

### 4.1 已核对的模型边界

- TypeSafe官方说明Jev目前只接受文本，不直接处理图片、音频、视频。
- DeepSeek官方说明当前 `deepseek-flash` 支持图片输入，接受JPEG、PNG、GIF、WebP。
- 这说明已有DeepSeek服务可能足够承担首版识图，仍需实际样本验证。
- 已查阅的视觉接口文档说明的是图片，不能据此承诺原生MP4视频或音轨理解。

因此架构建议：

```text
图片 → 视觉描述/OCR/可见产品线索 ─────────────┐
视频 → 画面理解 + 音频转写 + 时间戳对齐 ────┤
用户原话 + 已确认档案 ─────────────────────┤
                                         ↓
                          结构化文本证据 → Jev调度
                                         ↓
                           Skill + 产品资料 → 回复
```

### 4.2 “识图产品”拆成两步

1. 感知：读包装文字、品牌、规格、条码或外观线索，标记看不清/被遮挡的区域。
2. 匹配：与产品资料中的已知条目匹配，给出候选、证据和待确认项。

不能把视觉模型猜出的名称直接作为已确认productId。
当前仍是单产品项目：至少能区分“可能是目标产品”“不是目标产品”“无法确认”，不能所有图片都归到唯一产品。
用户确认后才将识别产品绑定为后续咨询上下文；价格、库存、成分事实仍需可靠资料。

### 4.3 “视频讲了什么”必须确认是否包含声音

视频往往同时含：画面动作、包装文字、字幕、旁白、背景音。
验收若要求完整内容总结，应同时处理画面和音频，或使用已验证支持两者的原生视频模型。
只抽帧看图时，必须明确“仅分析画面，未分析音轨”，不能声称已经理解整个视频。
采用抽帧方案时保留采样时刻及间隔；可能遗漏短暂动作，不能把没采到等同于没发生。

### 4.4 给 @mzt 的API选型交付要求

请提供一张已实测的接口卡，而不只是模型名称或网页链接：

- 服务商、完整模型ID、官方文档、端点和鉴权方式。
- 图片/视频/音频分别支持什么；视频是否包含音轨理解。
- 接受URL、上传file_id还是base64；是否必须公网可访问。
- 实测格式、大小、分辨率、视频时长限制；限制以账号和接口实测为准。
- 同步或异步调用、任务查询、取消及删除接口。
- 至少一个成功请求和响应样例，含实际耗时、计费单位、错误响应。
- 使用中文包装、模糊图片、有字幕/旁白视频测试；记录不确定性，不只展示最好的一例。
- 媒体是否被供应商保存、如何删除，账号区域和网络要求。

密钥通过本地/后端配置交接，不写进请求示例或Git。

### 4.5 我们的统一媒体接口

建议定义 `MediaAnalyzer`，隐藏不同供应商协议：

```text
analyzeImage(attachmentId, task, signal) → observations
analyzeVideo(attachmentId, task, signal) → job/result
```

观察结果至少包含：
- attachmentId、分析模型/版本、分析状态。
- 可观察事实、OCR文本、音频转写（如有）、不确定项。
- 带时间戳的视频片段；图像的可选位置引用。
- 产品候选与来源线索；模型估计不要伪装成经校准的概率。
- 是否覆盖音频、是否采样、被跳过的内容及分析失败原因。

### 4.6 必补的上传与会话机制

- 附件单独上传，返回服务端attachmentId；聊天消息支持纯文字、纯附件、混合输入。
- 不把原视频base64塞入目前的JSON聊天接口。
- 文件类型根据实际内容校验，并限制数量、大小、时长；压缩前后都有限额。
- 推荐比赛起点（待@mzt与业务确认）：图片JPEG/PNG/WebP，每次最多3张、每张10MiB；短视频先支持MP4、1个、60秒以内、50MiB以内。
- 上述是产品建议限额，不是供应商已确认能力；最终采用产品与供应商限制中更严格的一侧。
- 纯文本不等待其他媒体任务；每个媒体任务有queued/processing/succeeded/failed/cancelled状态。
- 视频分析用任务ID、进度和取消，不靠浏览器一直挂着一个请求；当前45秒咨询上限不能直接沿用为所有视频流程。
- 超时/失败只影响相关附件；已有文字仍能澄清或转人工，失败不能假装看过内容。
- 附件归属用户与会话；文件取回需授权，不能猜ID读取其他人的图片。
- 定义媒体保留期与删除行为；原始媒体不自动写进长期用户档案。
- 图片OCR、字幕、旁白是外部证据，不是可以覆盖Agent规则的系统指令。
- 媒体结果与用户陈述冲突时明确区分并追问，不悄悄改写用户事实。

### 4.7 验收样本

图片：清晰目标产品、其他产品、同图多产品、模糊/遮挡、只有图片、图文冲突。
视频：只有画面、带旁白、字幕与语音不同、目标动作短暂出现、无音轨、超限、取消、服务失败。
每个正常总结能定位到图片或视频时间段；未分析音轨时明确说明。

## 五、需求3：用户端与运营端分成两个前端应用

建议目录与路由：

```text
web/
├── customer/     # /chat/：聊天、媒体、自己的资料与反馈
├── operator/     # /ops/：Skill、模型、坐席、知识、追溯和看板
└── shared/       # 紫色主题、基础控件、API封装

server/           # 共用Agent、存储、API和模型连接
```

两个入口可以先同域名同进程部署，减少重复代码和跨域问题。
后端和数据库只有一套；双方看到的是同一会话与人工状态。

### 5.1 控件审查表（供 @mzt 的10.2体验检查）

| 现有/计划控件 | 用户端 | 运营端 | 处理建议 |
|---|---|---|---|
| 聊天输入、发送、取消 | 保留 | 测试台可有 | 取消状态明确 |
| 图片/视频选择、预览、移除、进度 | 新增 | 查看授权附件 | 先定义接口和限制 |
| 模型Key与Base URL | 不展示 | 保留 | 只给运营设置 |
| Skill上传/版本/启停 | 不展示 | 保留并完善 | 业务编辑入口 |
| 演示用户下拉选择 | 移出正式用户界面 | 测试模式保留 | 用户不能切换到别人档案 |
| 用户资料卡 | 只看/改自己的 | 按权限查看 | 普通表单替换JSON输入框 |
| route原始JSON | 移除 | 调试详情折叠 | 默认展示可读决策卡 |
| 处理状态 | 简短可读 | 完整时间线 | 不展示内部推理内容 |
| 产品依据 | 与本次回答相关的来源 | 资料维护/命中片段 | 不把全部后台资料常驻侧栏 |
| 请求人工 | 保留 | 待接管队列 | 用户不能自己点击坐席接管 |
| 人工回复/结束处理 | 接收状态和消息 | 坐席操作 | 状态由后端控制 |
| 有帮助/没解决/转人工 | 保留 | 汇总和追溯 | 同一反馈修改不重复计数 |
| 风险看板 | 不展示 | 保留 | 分母、样本与时间可追溯 |
| 初始化演示数据 | 不展示 | 演示管理保留 | 不覆盖真实业务资料 |
| 技术错误码/模型用量 | 用户看友好提示 | 保留诊断 | 错误详情不能包含密钥 |

@mzt检查时不只写“好看/不好看”，应记录：页面、用户目标、操作步骤、实际结果、期望结果、保留/新增/迁移/删除、优先级和截图。

### 5.2 服务端权限是拆分的一部分

仅把控件隐藏到另一个HTML文件，用户仍可能直接调用原来的设置/坐席接口。
必须同步做：

- 用户身份由后端会话/受控令牌确定，不能完全相信前端传入userId。
- 用户API只允许访问本人的会话、资料、附件和反馈。
- 运营身份才能上传Skill、编辑模型、导入资料、查看队列/看板、接管和回复。
- 同一域名时仍要处理会话Cookie、来源校验和写接口保护；HTTPS部署需修正当前仅接受http来源的逻辑。
- 比赛阶段可用简化的运营登录及匿名用户会话，不必先建完整CRM账号体系，但API检查必须真实存在。
- MCP继续作为受信应用入口，绑定用户或服务身份；不能绕过上述归属和角色检查。

## 六、推荐实施顺序与依赖

### P0-A：双端拆分与业务可观测性
- 建立customer/operator两个入口与服务端角色边界。
- 用户端移除模型配置、Skill管理、原始JSON和他人身份选择。
- 运营端提供决策卡、Skill版本/知识片段和模型错误诊断。
- 用同一条案例串起档案、决策、知识、回复、人工、反馈和统计。

### P0-B：Skill运行资源与验收完善
- 保留现有上传执行功能，补版本文档预览/导出与来源追溯。
- 业务同学上传自己的Skill做正例、反例、升级和停用测试。
- 确认是否真的要求Harness原生Skill列表；默认继续使用后端业务Skill + MCP架构。

### P0-C：图片最小闭环
- 并行由@mzt确认模型；开发先确定附件与MediaAnalyzer契约。
- 优先用已支持图片的DeepSeek Flash候选做实测，再决定是否换服务商。
- 跑通上传、OCR/产品线索、候选确认、Jev路由、知识回答及来源。

### P1：短视频
- 在确认“原生视频”还是“抽帧+转写”之后实现。
- 异步任务、音频覆盖声明、时间戳、取消、失败降级和费用控制一起验收。

本轮多模态属于对原15天单产品文字Demo的范围扩展，应显式调整排期，不能默认已有图片按钮就等于全部完成。

## 七、待团队确认的最小清单

1. Skill的目标是后端业务Agent执行，还是必须同时成为Harness原生Skill？推荐以前者为本阶段目标。
2. 视频“讲了什么”是否要求听音轨？推荐要求，但若首版仅画面，必须在UI和验收中明示。
3. 首版媒体格式、大小、时长和数量；是否接受先图片、后短视频。
4. 仍坚持单一产品，还是识别多个SKU？推荐先单产品/目标产品核对，保留“不是目标产品”。
5. 双端共享方式是同机演示、局域网还是公网？据此确定登录、附件地址和HTTPS要求。
6. @mzt交付模型接口卡及控件审查表；业务同学补媒体样本与正确/不可说内容。
