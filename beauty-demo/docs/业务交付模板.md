# 业务资料交付说明

请先打开 `content/templates/` 的JSON示例，再复制为自己的交付文件。所有 `.demo.json` 都是虚构样例，不能计入正式200条评论或50条Case。

## 业务A

### comments.demo.json：匿名评论批次

确认产品ID、稳定的评论ID、近半年起止日期，`dataKind` 改为 `business`。
`sources` 存来源名称、可追溯位置、采集时间；每条评论用 `sourceRef` 引用。
`publishedAt` 用真实发布日期，未知填 `null`。`collectedAt` 是采集时间，二者不可替代。
`tags` 由业务标注，例如刺激、紧绷、卡粉、起皮、搓泥、售后，可多标签。
不添加昵称/头像/主页字段；严格Schema会拒绝额外字段，但文本内是否包含个人信息仍需人工清洗。
重复导入依赖稳定ID，不要每次重新给同一条评论编号。

### insights.demo.json：第一版洞察格式

提供样本数、标签计数、方法说明、引用的评论ID、数据版本和范围。
计数需与不重复的证据ID数量一致，标签可重叠。
已有结构校验；独立洞察JSON存储导入尚待后续。当前看板已经直接根据已导入评论计算标签频率、共现和日期趋势。

## 业务B

### product.demo.json：产品事实与来源

选择一个产品，产品说明、成分、用法、注意事项和售后规则逐条写成 `facts`。
每条必须关联有效 `sourceId`。审核完成填 `approved`；`draft` 不会被知识接口返回。
`version` 是不可变版本，修订内容请换新版本；不要覆盖原版事实。

### skill.template.json：Skill接口定义

三份配置的ID需在首日统一，描述应包含职责及排除范围。
`knowledgeScopes` 从 product / after_sales / comment_insights 选择，表示允许使用的资料种类。
Skill可直接在“业务配置 · Skill上传”页面导入Markdown、JSON或ZIP。完整JSON模板已包含instructions/intents/requiresKnowledge/knowledge字段。
`config/business.demo.json` 只提供初始内置配置，网页上传的版本会持久化并立即进入运行注册表。详见 [组员上手与Skill上传](组员上手与Skill上传.md)。
资料事实仍需业务确认，reviewStatus用于标识，不再作为阻塞整个客服的全局开关。

### cases.demo.json：Case格式

首日确定4类意图、情绪标签和3个Skill的正式ID，然后替换示例占位值。
每条含用户原话、卡片上下文、期望风险/动作/人工要求、必含/禁含内容及来源。
遇到追问或人工分支，`primarySkill` 可为null，不强迫执行专家回答。
示例不是真值，需业务人员确认后形成至少50条金标。

## 交付顺序

1. 先给确定的产品ID、三份Skill定义和少量符合格式的真实资料。
2. 第2–3天逐步补齐产品知识与至少200条匿名有效评论。
3. 第4–5天提供50条Case及洞察，开发接入真实Jev路由回归。
4. 原始资料、洞察结论、来源清单保持相同版本，后续新增时注明修订。
