# 正式商品护理计划的导入契约

> 模板不是商品资料或自动审核结果。B/D 必须核对实物、官方用法、早晚适用范围、顺序及搭配风险，并留下审核依据；A 只让系统严格执行已提供的审核结论。

先导入 `dataKind: "business"` 的产品 JSON，确保每一步对应的 `usage` fact 为 `approved`、有 `sourceId`。随后由运营端“业务配置 → 正式护理计划”上传下列结构的 JSON（值均须替换为真实审核结果）：

```json
{
  "planId": "reviewed-routine-001",
  "version": "v1",
  "period": "evening",
  "reviewStatus": "approved",
  "reviewedBy": "B-D-审核人姓名",
  "reviewedAt": "2026-10-14T00:00:00Z",
  "scope": "明确写出适用人群、频次和前提；未审核的适用条件不得填写已审核。",
  "reviewSource": { "title": "经核对的书面计划名称", "locator": "内部审核记录的可追溯编号或页面" },
  "steps": [
    { "productId": "业务库中的真实商品ID", "productVersion": "商品当前版本", "usageFactId": "已审核的用法事实ID" }
  ]
}
```

`period` 可为 `morning` / `evening`；`steps` 按实际执行顺序填写 1–3 件，不能重复。必须同时满足商品版本、时段、选择顺序完全一致，用户本人确认后才开始；否则返回 `CARE_PLAN_NOT_REVIEWED`。商品更新版本会阻止旧计划用于新流程，历史流程保留建立时的步骤/来源快照。相同计划 ID 修改需递增 `version`，同一时段和商品顺序不能存在多个不同计划 ID。演示商品沿用原演示逻辑，**不能混入正式计划**。这套字段只验证审阅手续及结构，不能代替 B/D 对真假资料的实质审查。

启动已有 SQLite 数据库前先按 `npm run backup` 备份；代码会将 schema 5 升到 6，增加护理计划和不含原始媒体的调用记录。不要拿正式商品导入已有虚构演示数据的数据库。
